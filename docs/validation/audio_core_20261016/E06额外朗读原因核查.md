# E06 额外朗读原因核查

结论：额外语音已存在于单次非流式 MiMo 返回的原始 WAV，来源定位到服务返回阶段。现有证据不支持把它归因于本地拼接、100ms 起读处理或音频格式转换。具体是模型续写／停止异常，还是服务端其他原因，需要服务端跟踪记录或受控复现实验；当前不能下更细结论。

## 已核对的证据

- E06 正文只有两句、86 个字符：`Do you remember where we agreed to meet? Please wait beside the bridge until I arrive.`
- 用当前适配器、记录的正文／音色／模型重建请求，六条指纹均与生成时 SQLite 账本匹配。E06 用户指令是 `Use a steady audiobook pace. Read only the supplied text without omissions or additions.`，assistant 正文只包含上述两句；没有那段额外内容，也没有带历史消息。本检查使用离线响应替身，没有重发真实请求；它不是历史 HTTP 抓包。
- 目标正文在 assistant、风格指令在 user，符合 [MiMo 官方调用说明](https://mimo.mi.com/docs/zh-CN/quick-start/usage-guide/audio/speech-synthesis)。不能按普通聊天的角色习惯擅自交换。
- E06 使用 mimo-v2.5-tts、Milo、非流式 WAV。原始文件包含单个有效 RIFF/WAVE 数据块，24kHz 单声道、349440 样本，14.56 秒；其数据库哈希与试听副本一致。非流式路径仅解码响应音频的 base64 并保存原始字节，没有本地多段拼接。
- 双角色章节引用的 E06 PCM 与原始 PCM 逐样本一致，speed=1.0，render_operations=[]。该章节包含同一问题；后处理只是保留了异常。
- 同一句正文的 E02（Mia，7.04 秒）及 E04（Chloe，6.88 秒）经用户确认正常。E05（Milo 的另一条正文）也正常。因此不能凭这一条认定 Milo 全部不稳定，更不能将 1/6 当成总体故障率。
- 既有 ASR 在正确 16 词之后标出 15 个插入词，没有删除或替换，WER=15/16=0.9375。用户已确认额外内容；其大致转写中的 will 与 ASR 的 would 差异不影响“多读”的确认，逐词转写仍不是金标准。

## 核验登记与影响

已登记 E01～E05 正常、E06 内容失败，保留原始问题音频、原始探针清单及自动报告。另存带人工复核和音频指纹的派生清单；E06 verified=false，不进入声音库。Mia／Chloe 各有两条合格共同文本，Milo 仍缺合格的第二条，本次未额外建库。

本例属于 content 的 extra_reading，不能标成断音、漏音等四类边界阳性。它可作为一个真实人工确认的内容缺陷先导，但已参与规则与检查流程调试，不能冒称独立测试集。

此前 rate_drift 提示也需谨慎：预期 16 词除以含额外内容的音频时长，会把语速算低；这不能单独证明实际读得慢。用户未报告其他听感问题，原始机器提示保留为诊断。

## 后续修复方法

优先保持 Milo 音色和原文，只对 E06 做有次数上限的重新合成，强制绕过这份已知失败缓存，再做全文 ASR 对齐和人工听感验收。若重试仍多读，可按两个句子拆分，但要新增接缝复检。不要按 E02 的约 7 秒直接裁切 E06，避免误删正常句尾；也不要用淡入／降速处理内容多读。

现有统一核心已有固定逐字朗读提示、受限重采样／安全二分及候选复检入口；本次检查没有运行它们或新增 MiMo 请求。现有账本没有保存服务端 response id、finish_reason 或完整历史 HTTP 响应；因此不声称已定位到具体 EOS 参数，也不声称调整 temperature／stop 可解决。

机器可复核数据见 [v18 诊断 JSON](e06_extra_reading_diagnosis_v18.json)。本轮是数据与来源核查，没有修改合成源代码，未重复运行无关完整测试。
